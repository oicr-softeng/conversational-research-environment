Upgraded `tsup` from 6.7 to 8.5.1 in both modules, since 6.7 kept `apps/desktop`'s Vite from being hoisted.

- `tsup` 6.7 brings `yaml` 1 to the root `node_modules`, through `postcss-load-config` 3. Vite's optional peer `yaml@^2` then keeps Vite nested in the app's workspace, while Forge's Vite plugin is hoisted to the root, where it cannot find Vite
- The `target: 'node24'` lines left both `tsup` configurations. They were needed only because the esbuild 0.17.19 bundled with `tsup` 6.7 refused `es2024`. `tsup` takes its target from the `tsconfig` base again, so it follows a Node move without its own change
- The lockfile changes only `tsup`'s own dependencies
- `npm audit` now lists one low-severity advisory, GHSA-g7r4-m6w7-qqqr, for the esbuild 0.27.7 under `tsup`. It concerns esbuild's development server on Windows, which `tsup` builds never start. Its fix, esbuild 0.28.1, is outside `tsup` 8.5.1's `^0.27.0` range
- Build, typecheck, lint and `prettier --check modules scripts` pass on Node 24.21.0. Tests: `mcp-client` 70 in 15 suites and host-core 192 in 43, all passing, as before. Both modules' runtime exports are unchanged in ESM and CommonJS. Their declarations now mark type-only exports with `type`, and each module gains an `index.d.cts` beside `index.d.ts`

Scaffolded `apps/desktop` from Electron Forge 8's Vite template with TypeScript, on Electron 45.3.4, fitted per the migration plan's step 8. The template is its own commit, so the fitting reads as changes to it.

- `apps/desktop/package.json`: the app's `name` and `productName`, `private`, `0.0.0-dev`, AGPL and `repository`, with host-core and React as dependencies. TypeScript and `tsx` match the modules' ranges, and the template's oxlint, oxfmt and `release` script are gone
- `apps/desktop/eslint.config.js` extends the root one, with the app's own `tsconfig.json` for type information. Node globals are off in `src/renderer/`, which runs sandboxed
- `apps/desktop/forge.config.mts`: the `zip` and `dmg` makers for macOS only. Signing is ad-hoc for now, with `continueOnError: false`, and `optionsForFile` gives every binary `entitlements/ad-hoc.plist`: `allow-jit` and `disable-library-validation`. `entitlements/developer-id.plist` holds `allow-jit` alone, for when a Developer ID identity replaces `-`
- `npm run package -w apps/desktop` signs every executable in the bundle with only those two entitlements, under the hardened runtime. `npm start -w apps/desktop` starts the app, with its `userData` named after `productName`
- Forge 8's Vite plugin externalises only `electron` and Node's built-in modules and packages only `.vite/`, so host-core is bundled into the main build
- `require('electron')` now downloads Electron's binary on first use under plain Node, rather than in an install script. Another reason to keep `electron` imports out of what `tsx --test` loads
- `npm audit` adds a high-severity advisory with no fix, in `image-size`'s ICNS parser, through `appdmg` under the DMG maker. It parses only this repository's own icons, at build time
- npm 11 skipped the `node-gyp` builds of `fs-xattr` and `macos-alias`, which `appdmg` uses. Whether the DMG needs them is still to be checked

Hardened the app's main process against the migration plan's checklist for step 8, with the logic in modules that import only Electron's types, so that `tsx --test` loads them without Electron.

- The packaged renderer is served from the privileged scheme `app://renderer/`, through `protocol.handle`, in place of `file://`. `resolveAppFile` refuses any request that resolves outside the renderer's build, including through encoded separators, and any NUL byte or malformed escape
- Each response carries a content security policy in its headers. The packaged one allows only `'self'`. In development it also allows Vite's server and its WebSocket, and inline scripts and styles for React's refresh code
- The renderer runs on its own session, `persist:renderer`, so that its request filter leaves the main process's own `net.fetch` on the default session alone. The filter cancels any request outside the app's origins, and in development Vite's and DevTools' too. The session refuses every permission request, permission check and device
- `webPreferences` set `contextIsolation`, `sandbox` and `nodeIntegration: false` explicitly. `will-navigate` stops navigation to any other origin, and `setWindowOpenHandler` refuses every new window, opening only `https:` addresses on an allowlist, empty for now, in the person's browser
- `createIpcHandle` registers IPC handlers that refuse any message not from the main window's top frame, by `processId`, `frameToken` and origin. An ESLint rule stops `src/main/` from calling `ipcMain`'s registration methods directly. No channel exists yet
- The app takes the single-instance lock, and a second launch brings the existing window forward. DevTools opens in development only
- Checked in the running app through Chromium's remote debugging protocol, packaged and in development: the policy header is present, and a remote `fetch`, `window.open`, navigation away and camera access are all refused, with no Node globals in the page. A navigation started from outside the page fails with `net::ERR_BLOCKED_BY_CLIENT`, which shows the request filter working on its own. A second launch exited while the first kept running
- The first development run showed the request filter blocking DevTools, which loads through the page's session, so development builds also allow `devtools://devtools`
- Tests: the app's main process has 31, all passing
