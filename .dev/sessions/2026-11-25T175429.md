Decided how the desktop app's main process makes its network requests, so that requests to the model and to MCP servers honour the computer's proxy settings, PAC files and certificates.

- `.dev/docs/mcp-host/fetch-option.md`: the app hands both modules `net.fetch` on a dedicated in-memory session, wrapped so the modules never see Electron's errors, and moves to its own `fetch` on `net.request` only when an unavoidable redirect or a password proxy calls for it. The provider takes `fetch` in its constructor and the host takes one for every server, replacing the tech-debt entry's pass-through through host-core. The string-only type and the three levels of checks are recommendations awaiting a decision
- `.dev/docs/mcp-host/fetch-option.md`: findings that bind any implementation, all measured in Electron 45.3.4. `net.fetch` rejects any redirect in manual mode, and in follow mode, its default, carries `Authorization` to another origin. Cancelling its response body leaves the connection open, so a size limit must abort. Loopback is never proxied, even when a PAC file names a proxy for it
- `.dev/docs/mcp-host/scripts/fetch-option/`: the ten experiments, rerunnable from the repository, so that each finding can be checked again on the next Electron upgrade. None uses a self-signed HTTPS server, since this repository's credential-file hook blocks writing a private key, so trusting the system's certificates is unmeasured under every option

Gave both modules a `fetch` option, module side only, so the app can hand them Electron's `net.fetch` once host-core is connected to its main process.

- `modules/mcp-client`: `McpClientOptions.fetch` takes a string-only `Fetch`, which `toSdkFetch` in `src/fetch.ts` hands to the SDK's transport. Every request goes through it, OAuth discovery, registration and token requests included, and each address must be `http:` or `https:`, or it is refused with `UnsupportedSchemeError`, a `TypeError` naming only the scheme. `connect` checks `url` itself too, since the SDK reports a refusal from the fetch while connecting as an `SdkError`. Rejections pass through unconverted, so `Fetch`'s TSDoc states that a network failure must reject with a `TypeError`
- `modules/mcp-host-core`: `OpenAiCompatibleOptions.fetch` serves both of the provider's requests, and its constructor refuses a base URL that isn't `http:` or `https:`. `McpHostOptions.fetch` reaches every server's connection, and `ServerConfig.connection` leaves `fetch` out. `create` refuses a server URL with another scheme before connecting any server. The index re-exports `Fetch` and `UnsupportedSchemeError`
- Quick threat model:
    - Built: an injected `fetch` for both modules, with a scheme check on every request `mcp-client` makes and on the provider's base URL
    - Could go wrong: an address a server supplies, such as its OAuth metadata URL, names `file:` or a custom scheme, which an Electron `fetch` would read; one server's connection bypasses the proxy; a credential in a URL reaches an error message; a `fetch` rejecting with something other than a `TypeError` makes a failed OAuth discovery read as no metadata
    - Done about it: the scheme check sits in the wrapper every request passes through; `fetch` is host-wide and excluded from each server's configuration; error messages name the scheme only; the `TypeError` contract is stated in `Fetch`'s TSDoc and held by the app's function, whose Electron check gains a scenario for it
- Tests: `mcp-client` 84, from 70, and host-core 197, from 192, all passing. Removing the wrapper's scheme check, or the transport's use of the given `fetch`, fails the tests that cover each
